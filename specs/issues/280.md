# #280: Map string formats uuid / date-time / date to Python types

Issue: https://github.com/phalt/clientele/issues/280

## Summary

`get_type` only looks at `format` for numbers (`decimal`). Strings with `format: uuid`, `date-time` or `date` are generated as `str`, so callers lose pydantic validation and have to parse values themselves. FastAPI specs therefore round-trip to weaker types.

## Root cause

`utils.get_type` in `clientele/generators/shared/utils.py`, where the `DataType.STRING` branch ignores `format`.

## Proposed fix

In the string branch, map:

| format | type |
|---|---|
| `uuid` | `uuid.UUID` |
| `date-time` | `datetime.datetime` |
| `date` | `datetime.date` |
| `time` | `datetime.time` |
| `duration` | `datetime.timedelta` |

Unknown formats stay `str`. So does `uri`: `pydantic.AnyUrl` isn't a `str` subclass in pydantic v2 and normalises values (`https://example.com` becomes `https://example.com/`), so mapping it would break `str` usage and change round-tripped values for little validation gain. `email` also stays `str` (`pydantic.EmailStr` needs the optional `email-validator` package).

An inline `enum` with a `format` is handled by the `enum` branch at the top of `get_type` (added in #278) and stays a `typing.Literal` of its string values, so discriminators keep working and values match the wire format exactly.

Add `import datetime` and `import uuid` to the generated `schemas.py` template, and to `client.py` if parameter types can use them. Make sure query and path parameters with these types are serialized to strings on the request side.

Request side (`clientele/api/client.py`): path parameters go through `str()` in `APIClient._substitute_path`, and query parameters go to httpx, which also calls `str()`. That is fine for `uuid.UUID`, `datetime.date` and `datetime.time`, but `str(datetime)` uses a space separator (`2026-01-02 03:04:05+00:00`) and `str(timedelta)` isn't ISO 8601 (`1 day, 0:00:00`). Serialize these values (and lists of them) with pydantic's JSON mode before sending, so they match what pydantic emits in request bodies (`2026-01-02T03:04:05Z`, `P1D`).

This changes generated types. With the planned major bump, it's on by default; no flag.

## Tests

In `tests/generators/api/test_issue_280.py`:

- The repro from the issue: `id`, `at` and `on` validate to `UUID`, `datetime` and `date`.
- A unit test for each mapping in `get_type`, including nullable variants and unknown formats (still `str`).
- A generated client with a `format: date` query parameter sends `?on=2026-01-02`.
- Regenerate the test clients and check that the diff is limited to these fields. (None of the bundled specs (`best.json`, the FastAPI/DRF/Ninja examples) use these formats, and ruff removes the new imports when they're unused, so the regenerated clients don't change.)
