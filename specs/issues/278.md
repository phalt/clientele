# #278: Discriminated union fails when a member's tag is an inline multi-value enum

Issue: https://github.com/phalt/clientele/issues/278

## Summary

Discriminated `oneOf` unions generate `typing.Annotated[A | B, pydantic.Field(discriminator=...)]`. pydantic requires the discriminator on every member to be a `Literal`. `const` already becomes `typing.Literal[...]`, but an inline `{"type": "string", "enum": ["cat", "kitten"]}` becomes `str`, and importing `schemas.py` fails with `PydanticUserError: Model 'Cat' needs field 'kind' to be of type Literal`. pydantic/FastAPI emit this shape for `Literal["cat", "kitten"]`.

## Root cause

`utils.get_type` in `clientele/generators/shared/utils.py` handles `const`, but an inline `enum` falls through to its `type`.

## Proposed fix

In `get_type`, after the `const` check: if the schema has an `enum` (and no `$ref`), return `typing.Literal[v1, v2, ...]` using `repr` of each value. Keep nullability (`typing.Optional[...]` when `nullable`, or when `None` is in the enum). Top-level `components/schemas` enums still generate `enum.Enum` classes; only inline property enums change.

This is a typing change for existing users (`str` → `Literal`), so it goes in the major-version changelog.

## Tests

In `tests/generators/api/test_issue_278.py`:

- The repro spec from the issue imports, and `Owner.model_validate({"pet": {"kind": "kitten"}}).pet` is a `Cat`.
- An inline string enum property generates `typing.Literal["a", "b"]`.
- Inline integer enums generate `typing.Literal[1, 2]`.
- A nullable inline enum generates `typing.Optional[typing.Literal[...]]`.
- Top-level enum components are unchanged (still `enum.Enum`).
