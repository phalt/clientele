# #265: A no-content (204) response mixed with content responses is dropped

Issue: https://github.com/phalt/clientele/issues/265

## Summary

An endpoint that returns 204 (no body) on success, or 403/422 with JSON on error, generates a `response_map` and return type that leave out 204. A successful call then raises `APIException: Unexpected status code 204`. Endpoints that only return 204 work fine. A second problem from the comments: responses defined as a `$ref` to `components/responses` aren't dereferenced, so they look like no-content responses and are dropped too.

## Root cause

`clientele/generators/api/clients.py`:

- `get_response_class_names` records no-content codes as `"None"` but never adds them to `response_classes`, so the union that `generate_response_types` builds from those classes has no `None`. (The 204-only case works because `generate_response_types` returns `"None"` when there are no classes.)
- `get_response_map` filters `"None"` entries out of the map.
- Response `$ref`s (`#/components/responses/...`) are never resolved before the `content` check.

At runtime, `APIClient._parse_response` (`clientele/api/client.py` ~710) raises `APIException` for any status that isn't in `response_map` (~741), but it already returns `None` when the payload is empty. `request`/`arequest` don't validate `response_map`, so `{204: None}` already worked there at runtime; only the decorator path (`request_context._validate_response_map`) rejected it.

## Proposed fix

1. Resolve `#/components/responses/...` refs before inspecting `content`, using a helper alongside `utils.get_param_from_ref`.
2. Keep **2xx** no-content codes in `response_map` as `None` (e.g. `{204: None, 403: schemas.ErrorList}`), and add `None` to the result/return union when it's mixed with other classes. No-content error codes (e.g. a bare `404`) stay out of the map so they keep raising instead of returning a `None` that looks like success.
3. Make sure the runtime accepts `None` values in `response_map`: both checks in `request_context._validate_response_map` (value type, and value present in the `result` annotation, where `X | None` yields `NoneType`). The response path should return `None` for those codes without validating. Widen the `response_map` annotations in `client.py` and `request_context.py` to `typing.Mapping[int, type[typing.Any] | None]` (`Mapping`, because `dict` is invariant and existing `dict[int, type[Model]]` arguments would no longer type-check).
4. Regenerate the test clients; add a mixed 204/4xx endpoint to `example_openapi_specs/best.json`.

## Tests

- Generator (`tests/generators/api/test_issue_265.py`): a DELETE with `204` (no content), `403` and `422` produces `response_map={204: None, 403: ..., 422: ...}` and a return type that includes `None`.
- Generator: a response given as a `$ref` to `components/responses` with JSON content is included with its schema. (Neither `normalize_openapi_31_spec` nor cicerone resolves these: cicerone keeps the operation's response as a raw `{"$ref": ...}` dict, and the target is in `spec.components.responses`.)
- Generator: a no-content 4xx alongside content responses is not mapped to `None`.
- Generated client (sync and async): 204 returns `None`, 4xx returns the error model, unknown codes raise `APIException`.
- Runtime (`tests/api/test_issue_265.py`): a decorated function with `response_map={204: None, 403: Err}` returns `None` on 204 and `Err` on 403. Cover sync and async.
- Runtime: the same for `request`/`arequest`; unknown status codes still raise `APIException`; `None` in `response_map` without `None` in the `result` annotation is rejected at decoration time.
