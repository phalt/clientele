# #276: Request bodies drop fields set only by their defaults (2.3.1 regression)

Issue: https://github.com/phalt/clientele/issues/276

## Summary

2.3.1 changed request serialization to `model_dump(mode="json", exclude_unset=True)`, so the difference between an omitted field and an explicit `None` could reach the wire (PATCH semantics). The side effect: a field whose value comes from its declared default is now left out of the payload. Discriminator fields such as `action: Literal["add-user"] = "add-user"` disappear, and the server rejects the request (`union_tag_not_found`). The change shipped in a patch release.

## Root cause

`clientele/api/client.py`: `_prepare_data_payload` (~line 199, used by `request`/`arequest`) and the two `model_dump` calls in `_prepare_body` (~589 for a model instance passed as `data`, including one passed to a union-annotated `data`; ~593 for a dict validated into the annotated model) all pass `exclude_unset=True`. The issue's `clients.py:570/574` are stale. Streaming endpoints go through the same `_prepare_body`; nothing in `clientele/http` or the generated templates serialises bodies. Aliases come from `serialize_by_alias=True` in the generated models' `model_config` (`clientele/generators/shared/schemas.py`), not from the `model_dump` calls, so both modes keep them.

## Proposed fix

- Go back to including defaults by default, as 2.3.0 did.
- Make omitting unset fields opt-in through a `BaseConfig` field, e.g. `request_body_exclude_unset: bool = False`. Route all three call sites through one helper that reads it.
- Optionally, when the option is on, still always include `Literal`-typed fields that have defaults (discriminators). Decided: not done. Since #278 the issue's `action: {type: string, enum: [add-user], default: add-user}` is generated as `action: typing.Literal["add-user"] = "add-user"`, so in the opt-in mode it is left out like any other default. Callers who opt in pass discriminators explicitly; this is documented.
- The new field is inherited by the generated `Config`, so `config_py.jinja2` doesn't need it. pydantic-settings reads it from `REQUEST_BODY_EXCLUDE_UNSET` (no `env_prefix`; see #281).
- Changelog: note the behaviour change under the unreleased version in `CHANGELOG.md` (currently `2.4.0 UNRELEASED`), per the TODO convention. The release note in `TODO.md` covers whether that ships as 3.0.0.
- Depends on #268. Once fields with no `required` entry are `Optional = None`, the opt-in mode is what lets callers send real partial updates.

The reporter offered a PR. The maintainer handles that conversation.

## Interaction with #268

Since #268, a schema with no `required` list (DRF's `Patched*`) has all-optional fields, so in the default mode a partial update sends every field it didn't set: `PatchedUser(email="a@b.c")` sends `{"username": null, "email": "a@b.c", "is_active": true, "display-name": null}`. With `request_body_exclude_unset=True` it sends `{"email": "a@b.c"}`. The default stays "include", matching 2.3.0, pydantic and the issue; the changelog tells PATCH users to opt in.

## Tests

In `tests/api/test_issue_276.py`:

- `Notification(message="hi")` with a defaulted `action` serializes to `{"action": "add-user", "message": "hi"}` by default.
- With `request_body_exclude_unset=True`, the same model serializes to `{"message": "hi"}`.
- An explicit `None` is sent as `null` in both modes.
- Cover sync and async paths, `_prepare_data_payload`, and both `_prepare_body` call sites (model instance, also with a union annotation; dict validated into `model_instance`).
- A discriminated-union body in a client generated from a spec through `normalize_openapi_31_spec`.
- Alias serialization (2.3.1 change) still works in both modes.
